### Fixed

- **training**: `import_trainer_class` (and so `create_trainer`) now reports a trainer module's missing dependency as a missing dependency instead of as a provider name that does not exist. The resolver's third rung imports `strands_robots.training.<provider>`, and that import fails two distinguishable ways: the module is absent, which means the caller's provider name is unknown and the useful answer is the list of names that are known; or the module is present and something *it* imports is absent, which means the name was right and the useful answer is the missing distribution. The handler caught `ImportError` outright and fell through to `ValueError: No trainer registered for provider '<name>'. Available trainers: [...]` for both, so a caller whose spelling was correct was sent to go and check the spelling. Measured on an install without `torch`: `import_trainer_class("rl")` reported that unknown-provider `ValueError` while the underlying failure was `ModuleNotFoundError: No module named 'torch'` - and `strands_robots.training.rl` is a shipped module under exactly that prefix whose own docstring records that importing it imports `torch`, which arrives through an extra. The handler is now narrowed to the absence of the provider module itself (compared on the `ModuleNotFoundError`'s own `name`, which for a missing submodule is its full dotted path), and the class lookup moved into an `else` so only the import is guarded; anything else surfaces. This is the contract the two sibling resolvers already had - `import_policy_class` re-raises through an error naming the install remedy, `import_transform_class` re-raises the original, each documenting it in its own `Raises:` block - so the trainer resolver's docstring, which advertises that its resolution order mirrors theirs, is now accurate about the failures too. The rule is pinned over a derived inventory of every resolver that imports a caller-named module under `strands_robots.`, so a fourth one is held to it on arrival rather than repeating this.
