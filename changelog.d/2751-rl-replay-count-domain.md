### Fixed

- **training**: FastSAC now reports a replay count it cannot honor instead of accepting it silently or raising a deep stack trace. `RLTrainSpec.buffer_size`, `batch_size` and `gradient_steps` are the three caller-supplied counts of a SAC replay loop - the buffer capacity, the transitions sampled per gradient step, and the SAC updates per iteration - and each was compared with a bare `value <= 0` test. Because each is consumed directly as a count (a tensor dimension built in `setup`, a `ReplayBuffer.sample` size, a `range()` bound in the update loop), such a test is weaker than the field demands: measured on the MuJoCo reach env, `buffer_size=True` built a one-slot buffer that never reached `learning_starts`, so **zero** gradient updates ran, yet the run reported `status="success"` and "10 iterations x 4 steps complete"; `buffer_size=0.5` raised `IndexError` from `ReplayBuffer.add` (`int(0.5) == 0`, a zero-capacity buffer); `batch_size=0.5` / `batch_size=True` raised `TypeError` from `torch.randint` in `ReplayBuffer.sample`; `gradient_steps=0.5` raised `TypeError` from `range()` in the update loop - each after `setup` had built the environment, the networks, the optimizers and the replay buffer, which is the cost a read-only preflight exists to precede - and `"256"` / `None` raised `TypeError` out of the comparison itself, from a method documented to *return* problems. The three counts now go through the shared `positive_count_error` domain that `run_size_problems` already uses for the supervised `steps` / `global_batch_size` pair, via a new `rl_replay_problems` gate (the SAC peer of `rl_run_size_problems`); only FastSAC reads these fields, so it is scoped to them rather than applied to every backend. FastSAC's `learning_starts >= batch_size` relation now consults the same domain before comparing, so a non-comparable `batch_size` is reported rather than reaching `<`.
