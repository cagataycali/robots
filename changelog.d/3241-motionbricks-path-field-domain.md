### Fixed

- `MotionBricksConfig.skeleton_xml` and `MotionBricksConfig.scene_xml` are now held to the same path domain as `result_dir`, instead of to no check at all. Of the config's eleven declared fields these two were the only ones `__post_init__` never mentioned, so every failure the `result_dir` path domain exists to prevent reproduced on them unchanged: a `pathlib.Path` was stored unnormalised, so a config built from one compared unequal to the identical config built from a `str`; a `list` left this frozen - therefore hashable - dataclass unhashable; and a value no path can be read from, such as `123`, travelled to the generator to fail inside upstream `motionbricks` rather than being reported here. A falsy value fared worse rather than better: `result_dir=0` was at least refused, whereas `skeleton_xml=0` and `skeleton_xml=""` were accepted and then discarded by `config.skeleton_xml or <derived default>` in `_MotionBricksAgentAdapter.build`, so the generator was built against the derived skeleton and the run reported success - indistinguishable, at every later surface, from the `skeleton_xml=None` that asks for exactly that. All three path fields now go through one module-local `_normalised_path_field`, which keeps `None` first-class for the two optional ones because that is how a caller asks the builder to derive the path, and the builder reads `is None` rather than a truthiness test. `result_dir`'s refusal text is unchanged. Pinned by `TestOptionalPathFieldsShareThatDomain` in `tests/policies/motionbricks/test_config_value_domain.py`, which parametrises the axis over both fields, and by `test_the_skeleton_the_caller_named_is_the_skeleton_the_generator_is_built_with` in `tests/policies/motionbricks/test_agent_adapter_build.py`, which reads what reached `full_navigation_agent(skeleton_xml=...)` through the stub build seam; 38 of the 44 new cells fail on the pre-fix tree and the remaining 6 pass on both, pinning that an omitted path still derives and a usable one still builds unchanged.
