### Added: `Robot("microduck")` works out of the box - discovery, API 31 and the full operator vocabulary

The native Microduck driver spoke `duck-ipc-proto` API 16 and exposed three verbs (`sensors`, `status`, `stop`); everything the pad, `duckctl` and `robotctl` give an operator had to go through `send_action` dicts, and a robot anywhere but `/run/robotd.sock` needed a hand-forwarded socket passed as `port=`. robotd 0.14.1 answers `api_version: 31`, so the handshake gate refused every current duck - and because robotd bumps that number for additive methods too and answers a call it cannot serve with an error naming the method or parameter, a skew is now logged rather than refused. The driver's frames are checked against 0.14.1 (API 31), and it finds the robot itself: `port` (a path or `ssh://[user@]host`), then `$MICRODUCK_SOCKET`, then `$MICRODUCK_HOST` (the driver runs `ssh -N -L` with `BatchMode`, `ExitOnForwardFailure` and `StreamLocalBindUnlink`, forwarding robotd's, mediad's and tofd's sockets; user `radxa` or `$DUCK_BOARD_USER`), then the on-robot default - and a "did not answer" refusal names which of those to set. `mode="auto"` asks the driver's new `probe_hardware()` before the serial scan, so `Robot("microduck")` is the real robot when a robotd answers and MuJoCo when none does; a probe that raises is a probe that found nothing.

The agent tool's `action` enum is now generated from one dispatch table of 32 verbs: `move` (a twist the driver re-sends at 20 Hz for `duration` seconds and ends with a zero twist, because robotd zeroes a twist older than its 0.5 s deadman; refused before the wire outside the pad's envelope for the current mode since robotd clamps nothing there, and refused while a skill policy is running), `head`, `look_at` (a point in the robot frame, solved and held on the robot; `neck_pitch` is the required posture the IK aims around), `pose` (held to the trained range `PoseParams` documents and the robot does not enforce), `mouth`, `do` and `skills` (the skill list is the one *this* robot sends on `robot.subscribe`/`robot.policies`), `sit`/`stand` (only in the direction the robot's `sitting` flag says is a change), `enable`/`disable`, `relax`/`init`/`reboot_motors` (each needs `confirm=true`), `sounds`/`play_sound` (`wheee` refused: a pad-trigger ride the driver cannot hold), `theremin`, `mode`/`set_mode`, `policies`/`load_policy`/`reload_policies`, `health` (adds `imu_frozen`), `version`, `model`, `odometry`, `monitor` (a `robotctl monitor` row), `camera` (one `media.frame` decoded to a JPEG with the mount rotation applied) and `tof` (one depth frame summarised).

Every write that answers with an `IntentResult` reports robotd's verdict: `accepted: false` is the verb's refusal carrying robotd's `reason`, and a declined intent does not clear the `motion_stopped` latch. `status`, `sensors`, `sounds` and `odometry` answer from the cache and never connect; every other verb connects on first use so `Agent(tools=[Robot("microduck", mode="real")])` needs no `connect_eagerly` line. `ssh_forward_argv`'s `connect_timeout` takes the shared positive-finite domain the library's other three surfaces of that knob take, so a budget ssh cannot spend is refused by name instead of rounding to a silent one second. `camera`'s `save_path` names a file inside the frame root (`$STRANDS_ROBOTS_MICRODUCK_FRAME_ROOT`, default `~/.strands_robots/microduck/frames/`) and is refused when it leaves it, so a value a model filled in cannot write JPEG bytes over an arbitrary file this process can reach. The mock robotd in `tests/mocks` speaks the v31 shapes and `tests/drivers/microduck/test_microduck_full_vocabulary.py` drives every verb over a real unix socket. Physical motion on a duck has not been exercised by this change.
