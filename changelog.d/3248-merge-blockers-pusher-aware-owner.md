### Fixed

- `scripts/check_merge_blockers.py` names the party who owes the next action on an unreviewed pull request as `a reviewer other than the pusher` wherever the branch carries `require_last_push_approval`, instead of `any reviewer`. The party was derived from the outcome alone, which cannot express it: whether any reviewer's approval would count depends on who pushed the head, a fact the evaluator has already resolved and prints in the same report one row above the party it contradicted. Measured live on 2026-09-06, #3205 and #3212 both read `missing-approval` / "any reviewer" beside "head pushed by cagataycali", whose approval cannot satisfy the count - so the review round the report invited would have arrived at `pusher-only-approval`, the state #2907 has been blocked in since that same account approved it on 2026-09-04. The outcome is unchanged, deliberately: it also decides gating, finding and exit status, and an unreviewed pull request remains the ordinary state rather than becoming a finding because the eligible set is narrower.

  Pinned by `tests/test_merge_blockers.py::test_an_absent_approval_names_a_party_whose_approval_would_actually_count` (table-driven over the rule and the pusher, with the branch-does-not-carry-it and pusher-undetermined halves as controls that must keep reading `any reviewer`), `::test_an_absent_approval_and_a_pusher_only_one_name_the_same_party` (the two states are one review round apart and cannot name different people) and `::test_narrowing_the_eligible_set_does_not_promote_the_ordinary_state_to_a_finding`. Four existing pins asserted the old party on a fixture whose branch carries the rule; each is retargeted with its original point intact.
