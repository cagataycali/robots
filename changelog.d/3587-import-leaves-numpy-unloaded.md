### Fixed: `import strands_robots` leaves numpy out of `sys.modules`, so a narrowed `--cov=strands_robots.<sub>` run works again

The package root promised a bare import that pulls in neither torch, lerobot, numpy nor mujoco, and initialised numpy through two chains on every import. `strands_robots.policies` exported `Cosmos3Policy` eagerly (three numpy-importing modules) and `policies.base` imported numpy for a single annotation; both now resolve lazily, `Cosmos3Policy` through the package's PEP 562 `__getattr__` beside `list_policy_types`. And the `MUJOCO_GL` selector the root runs at import time lived in `simulation.mujoco.backend`, so importing it executed `simulation/__init__` -> `SimEngine` -> the policy runner -> the rendering package, twelve numpy-importing modules for a function that reads `os.environ`. That stdlib-only cluster now lives in `strands_robots._mujoco_gl`, beside `_dyld`, the other import-time shim; the backend re-imports the helpers its rendering probes still call, and `doctor` reads the vocabulary from the leaf.

This is the whole cause of #3587: coverage resolves a dotted source with `find_spec` inside `sys_modules_saved()`, so a numpy the parent package initialised is dropped from `sys.modules` and the next `import numpy` re-executes its Python layer over an already-initialised C extension. Measured on `tests/simulation/isaac/` under `--cov=strands_robots.simulation`: 149 of 2268 failed on `float()` of a foreign `_NoValue` at `4578a5f6f`, and on the current numpy the run does not start at all (`ImportError: cannot load module more than once per process`); after this change it reports the same 2206 passed / 50 skipped with and without coverage. A test that patches one of the GL helpers now sets it on `strands_robots._mujoco_gl` - a patch on the backend's re-imported name is not the one the selector reads.
