### Fixed

- **simulation/isaac**: the MJCF scene loader now reads `<compiler>` and `<asset>` from the whole model rather than the top file's direct children. MuJoCo splices `<include file=...>`, so both are model-global, and the loader disagreed with MuJoCo in two directions on models MuJoCo compiles. An `<asset>` block in an included fragment left the mesh registry empty, so the body silently fell back to the hardcoded 0.05 m box proxy #2459 removed while `load_scene` reported a successful scene - a pixel-conditioned policy evaluated against a 5 cm cube standing in for a 0.4 m object. A `<compiler meshdir>` in an included fragment resolved the mesh against the model directory instead, so the existence check refused a file that is present and the whole scene load raised, losing every object rather than one and blaming a missing asset for a mesh sitting where the fragment said. `assets/download._mjcf_mesh_subdir` already states the rule for the robot-asset path and names the harm, "reports a mesh that is present as absent", and `mujoco/simulation._ensure_meshes` already follows includes for it. A comment claiming the first case could not occur because MuJoCo refuses to compile such a scene is corrected: MuJoCo compiles it. Nested includes chain, each resolved against the including file's directory, and a missing, unreadable, malformed or cyclic include contributes nothing rather than failing the scene. Document-order precedence is unchanged and now pinned against MuJoCo's own choice - within one `<compiler>` element `meshdir` overrides `assetdir`, but a later element overrides an earlier one - which is why the search directory is not delegated to `_mjcf_mesh_subdir`: it prefers `meshdir` wherever any fragment declares it and would answer the second case the way MuJoCo does not. Object selection is untouched; `<worldbody>` is still read from the top file only.
