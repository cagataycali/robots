### Fixed

- `VeraConfig.server_ready_timeout` is held to the shared positive-finite-seconds domain, and `VERA_SERVER_READY_TIMEOUT` is read. It was the only numeric field on the dataclass with no domain - both ports, `render_width` and `motion_plan_scale` are each checked on the effective value - and the environment variable's only two appearances in the tree were the two message strings naming it as the remedy, so following the advice a readiness timeout gives changed nothing: the next attempt failed after the same 600 seconds with the same sentence pointing at the same variable. The missing domain was reachable every way it can be wrong: `inf` made `deadline` infinite so the wait could not end (and the raise is what tears the launched server down), `nan` is below nothing so the same loop could not begin - zero port probes, a healthy server torn down as unready - `0`/negative/`True` did that in plainer words, and a `str`, the shape an environment value has, raised `TypeError` out of the wait past its documented failure channel. `None` now resolves to the environment else 600, the sentinel every other env-overridable field here uses, so the observable default is unchanged; `0` is not an opt-out, for the reason it is not one for `motion_plan_scale`.

  Pinned by `tests/policies/vera/test_vera_server_ready_timeout_domain.py` (the domain, table-driven over both the keyword and the environment spelling, plus a walk of the operator's own loop: time out, read the variable name out of the message, export it, and wait again). `test_vera_server_lifecycle.py::test_times_out_when_never_ready` drives the clock instead of passing a zero budget, matching the docker runner's readiness test beside it.
