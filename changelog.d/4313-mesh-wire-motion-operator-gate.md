### Fixed: a mesh command that moves real hardware passes the operator gate on the robot host

`Mesh._dispatch` used to hand a wire `execute` / `start` straight to the rollout and `teleop_receive` straight to an input stream onto the motor bus, so any peer admitted to the mesh could drive a physical arm with nobody asked. A hardware peer now runs the shared `gate_motion` path before dispatch: a dashboard grant for the exact call is spent, `STRANDS_ROBOT_COMMAND_ALLOW` on the robot host pre-approves the verb (the variable the hardware `Robot` tool already reads), `BYPASS_TOOL_CONSENT=true` lifts the gate with a WARNING, and otherwise the command is refused with the remedy and a `wire_motion_refused` audit record. `stop` and `teleop_stop` are never gated, simulation peers are never gated, and `source_peer_id` / `device_name` are part of a motion grant's identity (f011).
