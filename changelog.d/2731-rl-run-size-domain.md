### Fixed

- **training**: both RL backends now report a run size they cannot honor, instead of returning an empty list - which `Trainer.validate`'s contract defines as "the spec is launchable". `RLTrainSpec.total_timesteps` and `rollout_steps` are the two caller-supplied factors of the one loop bound each trainer derives, `max(1, total_timesteps // (rollout_steps * num_envs))`, iterated as `range(num_iters)`, and each was compared with a bare `value <= 0` test. Because the bound is *derived* through that `max(1, ...)` clamp, such a test is much weaker here than the same test on a field consumed directly: measured on both trainers over a 16-step run with `rollout_steps=4`, `True`, `0.5`, `nan` and `inf` each reported `status="success"` after exactly **one** iteration, wrote a checkpoint and announced `"1 iterations x 4 steps complete"` for a run asked to be tens of thousands of steps long (`inf // 4` is `nan`, and `max(1, nan)` is `1` - `nan` compares false against everything, so an unbounded budget landed in the silent column rather than the raising one). A fraction that *does* divide, `100.5 // 4 == 25.0`, gave `range()` a float bound and raised `TypeError: 'float' object cannot be interpreted as an integer` only after `setup` had built the environment, the networks, the optimizers and - for FastSAC - the replay buffer, which is the cost a read-only preflight exists to precede. `"16"` and `None` raised `TypeError` out of the comparison itself, from a method documented to *return* problems. `rollout_steps=True` changed the shape of the run rather than its length: it makes `steps_per_iter` one, so FastSAC ran 16 single-step iterations instead of 4 of 4 under a successful result, and PPO normalized advantages over a length-one batch - whose standard deviation is `nan` - and failed inside `torch.distributions.Normal`'s constraint with a message naming neither the field nor the run. Both factors now go through the shared `positive_count_error` domain that `run_size_problems` already uses for the supervised `steps` / `global_batch_size` pair; the domain is shared, only the field sets differ, which is why this is a second gate rather than part of that one (per `TrainSpec`, a backend must not be refused for a field it never reads). `num_envs`, the third factor of `steps_per_iter`, deliberately stays per-backend because the accepted sets differ - PPO parallelizes and accepts any count `>= 1`, the MuJoCo-backed FastSAC is single-env and requires exactly `1` - so it is not one shared domain. PPO's `rollout_steps % num_mini_batches` relation now consults the same domain before dividing, so a string no longer reaches `%` as string formatting and `nan` is no longer reported as *indivisible*, which named the wrong problem.
