### Fixed: `describe()` advertised two camera/randomization signatures out of parameter order

The Isaac backend advertised `add_camera(name, position, target, width, height, fov)` while the method declares `(name, position, target, fov, width, height, parent_body)`, and the Newton backend advertised `randomize(..., mass_range, friction_range, color_range, ...)` against a `(..., color_range, friction_range, mass_range, ...)` method. `describe()` is the discovery surface an agent reads before building a call, so an agent copying either string into a positional call landed `fov` on `width` (and the range multipliers on each other), and the Isaac string dropped `parent_body` entirely so a wrist-mounted camera was undiscoverable.

The existing per-backend describe check pinned that every advertised keyword EXISTS and that every required keyword is PRESENT, but never read the order, so a reordering passed silently. Both signature strings are corrected, and the check gains `test_every_advertised_signature_preserves_parameter_order`: the advertised parameters that name real parameters must be an in-order subsequence of the real signature (omitting a trailing optional one stays a legal abbreviation), enforced statically across all four describe surfaces (base, MuJoCo, Newton, Isaac) with no simulator runtime.
