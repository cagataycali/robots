### Fixed: a ROS 2 topic name is judged by one rule, and it is the mapping's own

The ROS 2 topic-name rule is answered by one owner, and it is the rule the ROS 2 mapping states rather than a subset of it. `strands_robots/rtps/mangling.py` cites the "Topic and Service name mapping to DDS" article and implemented four fewer clauses than the article lists, and the same pattern was spelled three times byte-identically -- in the mangling, in the `use_rtps` tool, and in `RtpsRobot` -- so a name any one of them admitted was a name all three admitted. Measured on the shipped rule, `dds_topic_name` minted a DDS topic for `//cmd_vel`, `/a//b` (an empty name token, which the article spells out as "the name `//bar` is not allowed"), `/1cam`, `/a/2b` (a token starting with a digit), `/a__b` (repeated underscores), and a 301-character name whose DDS form ran 47 characters past the 256-character bound the article puts on the DDS name; `ros_topic_name`, whose docstring says it checks the name it recovers because "a DDS graph carries topics no ROS 2 node published", handed all of those back as recovered ROS 2 names. Nothing downstream reports the divergence, because DDS matches by topic name: the participant advertises a name `rclpy` refuses at `create_publisher` and simply never finds a peer, which is the same silent failure this module already refuses a service interface to avoid. The rule now lives once as `ROS_TOPIC_RE` plus `MAX_DDS_TOPIC_LENGTH`, the length bound is checked on the mangled form in both directions because that is the name the article bounds, and `ros_topic_error` names the single clause a refused name broke instead of reporting one "invalid topic name" for six different mistakes. A digit inside a token (`/turtle1/cmd_vel`) and a single leading underscore (`/_hidden/x`, a ROS 2 hidden topic) stay legal, so the rule narrows to the article's set and not to something tighter.

`RosTelemetryBase._safe`, the single owner of the topic names both hardware bridges publish on and documented as mapping a name to a *valid* ROS 2 topic segment, is now held to that rule -- previously it disagreed with it in both directions. `str.isalnum` is true of every Unicode letter and digit rather than of the ROS 2 character set, so a camera named `a non-ASCII letter or a superscript digit produced a topic the tree's own mangling then refused, surfacing from inside a telemetry publish rather than at the name that caused it; and a camera named `0` or `3rd_person`, or one carrying the `arm0__wrist` spelling this tree already uses for a namespaced camera feature, produced a token ROS 2 refuses that the mangling minted anyway. Numeric names are not a contrived input here: an so101's sim observation keys are `1` through `6`, and a camera keyed by its device index is the ordinary case. Such a camera now publishes on `/<robot>/camera_0/image_raw`, with the digits carried rather than dropped so two index-named cameras stay on two topics. Names that were already valid are byte-identical: `/so101/joint_states`, `/so101/front/image_raw` and `/so101/wrist_cam/image_raw` are unchanged.
