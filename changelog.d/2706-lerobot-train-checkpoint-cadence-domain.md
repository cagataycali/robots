### Fixed

- **tools/lerobot_train**: `save_freq` is now held to the same `int` requirement as the run-size numerics beside it in the same detached argv, and refused at the dispatch boundary. It was the last token in that argv carried through unchecked, and it feeds two flags: `--save_freq=` always, and `--eval_steps=` whenever a validation split is requested. `save_freq=2.7` (or `5000.0`, `True`, `nan`, `inf`) reached lerobot's plain `int` field, which decodes the token with `int(...)` and refuses every one of them - inside the detached process, minutes after the tool reported the run started with a pid; and `save_freq="5000"` raised a bare `TypeError` out of the `save_freq if save_freq > 0 else steps` selector, surfacing as `Tool execution failed: '>' not supported between instances of 'str' and 'int'`, a message naming neither the parameter nor the tool. The refusal now names both and quotes the value. The **floor is deliberately not part of this domain**: lerobot documents a non-positive `save_freq` as "disables periodic saving" and `should_save_checkpoint` implements it, so `0` and a negative are still accepted and still select the single-final-evaluation fallback. Like `device`, the check sits after the resume early return, so a resumed run whose argv carries neither flag is not refused for a value it does not use.
