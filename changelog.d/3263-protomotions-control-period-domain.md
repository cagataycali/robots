### Fixed

- **policies/protomotions**: `ProtoMotionsConfig.control_dt` now goes through the shared `positive_finite_number_error` domain when the config is built, and `load_config_from_yaml` hands the sidecar's `timing.control_dt` through RAW instead of coercing it with `float()` first. It is the one field of the timing block the control path spends: it is the period `MotionPlayer` RESAMPLES a reference motion onto, so it fixes how many frames one clip becomes, and `ProtoMotionsPolicy.get_actions` advances the playhead exactly one of those frames per tick - the frame count is the reference motion's duration in ticks. The removed coercion is precisely the laundering the two comments directly above it already name: `anchor_body_index` and `action_ema_alpha` are each "handed through raw, not through `int()`" because coercing first turned a yaml `true` into a valid-looking value before the domain could see it, and three lines below the second of those comments the timing block did it anyway. Measured by resampling a 3-second 30 fps clip and asking the tracker's default lookahead offsets `(1, 2, 4, 8)` for frames ahead of the playhead: a sidecar `control_dt: true` resolved to a **1-second** control period and produced a **4-frame** clip, so two of the four offsets read past its end from the very first tick; `-0.02` and `inf` each collapsed the clip to a **single frame** - `max(1, round(motion_length / control_dt) + 1)` is non-positive for both - which the index clamp in `get_state_at_frame` then served for every tick of the episode, a tracker that reports a motion and holds one pose. `0` and `false` were accepted by the config and surfaced only as `ZeroDivisionError` out of the loader's own `logger.info` argument (`1.0 / cfg.control_dt`), so the only thing in the tree that objected was a log format string, and a directly constructed `ProtoMotionsConfig(control_dt=0)` was accepted with nothing raised at all. `nan` reached `int(round(...))` inside the resampler and raised "cannot convert float NaN to integer" there, naming neither the field nor the sidecar it came from. `MotionPlayer` holds both places a period enters it to the same domain, because a cache dict's own `control_dt` OUTRANKS the `control_dt=` argument - gating only the config would have left a caller who passed a good period playing a clip at an unusable one. A string spelling such as `control_dt: "0.02"` is now refused where `float()` used to accept it; the two gated siblings already refuse strings, so this is the timing block joining them rather than a new kind of rule. Nothing that named a real rate changes: `0.02`, `0.04`, `1/30` and a NumPy scalar read out of a config array all still load, normalised to a plain `float`. `physics_dt` and `decimation` are deliberately left alone and the boundary is pinned - no reader in this package consumes either, so refusing a value there would change which sidecars load with no behaviour to protect, and their documented `control_dt / physics_dt` relation stays unchecked for the same reason.
