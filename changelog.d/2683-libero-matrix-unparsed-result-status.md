### Fixed: a matrix row whose result line could not be read no longer reports `ok`

`examples/libero/libero_backend_matrix.py` recorded a row as `ok` whenever the per-backend driver exited 0, without checking that it had read the row's numbers - `ok` was a verdict about the exit code alone. A driver that exits 0 but prints no result line, or one whose line has drifted out of `_RE_RESULT`'s shape, therefore reported the same status as a row that measured cleanly, differing only in two `--` cells that a reader of the `status` column never sees. Measured against the real `_run_one`: a driver printing nothing and a driver printing an unparseable line both came back `RowResult(success_rate=None, wall_time=None, status='ok')`, byte-identical to the status of a row that measured 0.40.

Such a row now records `incomplete (driver exited 0 but printed no parseable result line)`. It is deliberately not a `skip (...)`, which means the driver refused to run - the documented normal case on a host without Isaac Sim - whereas this driver ran to completion, so the reader is pointed at a driver/parser format disagreement rather than at a missing backend. The `ok` spelling for a row that did measure is unchanged, and a non-zero exit keeps its exit-code-derived skip reason.

`_parse_driver_output`'s docstring justified the old `ok` with a driver that "exited early before the eval started (e.g., HF token missing for `--policy=groot`)". That path no longer reaches it: `run.py` raises on a refused setup step and on an eval it cannot complete, and its `main` has no return statement at all, so such a run exits non-zero and is recorded by exit code. The docstring now states the reachable cause, and that reasoning is pinned by a test rather than left as prose. Whether an `incomplete` row should also make the matrix process exit non-zero is a separate contract for its callers and stays out of scope, with a control test that fails if it is changed without deciding it.
