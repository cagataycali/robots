# Simulation troubleshooting

Install and hardware gotchas are on the [troubleshooting sheet](../troubleshooting.md);
this page is the simulation half of the same table.

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| `GLXBadFBConfig` (Linux) | Missing OSMesa | `sudo apt install libosmesa6-dev` + `export MUJOCO_GL=osmesa` |
| Black frames from `render(...)` | Headless, no GL backend | `export MUJOCO_GL=osmesa` (Linux) or `=egl` |
| Rendering very slow (~100x), warning `rendering on a CPU software rasterizer` | `MUJOCO_GL=egl` but NVIDIA's EGL vendor does not answer, so EGL falls back to Mesa `llvmpipe` (CPU) | The warning names the cause still standing. On an NVIDIA host the library stages a vendor ICD in `~/.strands_robots/egl_vendor.d/` and points glvnd at it via `__EGL_VENDOR_LIBRARY_FILENAMES` (no root; set the variable yourself to opt out). If it persists: ensure `NVIDIA_DRIVER_CAPABILITIES` includes `graphics`; register the ICD system-wide (`/usr/share/glvnd/egl_vendor.d/10_nvidia.json` = `{"file_format_version":"1.0.0","ICD":{"library_path":"libEGL_nvidia.so.0"}}`); or check `nvidia-smi` works in this process, since a driver present but unreachable reports only as this fallback. Verify with `GL_RENDERER` - the NVIDIA GPU, not `llvmpipe`. |
| `Robot("foo")` raises ValueError | Unknown name | Check `list_robots("all")`; or pass `urdf_path=...` |
| `add_robot` refuses with `is registered but its model file is not on disk` | The name is correct - the registry knows the robot, its MJCF is just not present on any asset search path | Do what the refusal names: it prints the `<dir>/<model_xml>` it looked for and every path searched. An entry it reports as `auto_download=false` (`google_robot`, `trossen_wxai`) never fetches - place the file there yourself, under `STRANDS_ASSETS_DIR`. Any other entry is fetchable: `download_assets(robots="<name>")` |
| Sim hangs on `create_world` | Asset download | Wait - first call downloads MJCF, then cached |
| `download_assets` reports `failed: fetched tree has no <model_xml>` | The tree is on disk but holds no file the entry declares as this robot's model, so `resolve_model_path` cannot find it. Clone routes fetch their source repository at HEAD, so an upstream rename retires the declared name (`so101` at Menagerie HEAD ships `so101.xml`, not the declared `so101_new_calib.xml`) | The verdict lists the model files that did arrive. Install `robot_descriptions` (`uv pip install strands-robots[sim-mujoco]`), which pins a commit rather than following HEAD, or point the entry at a file that arrived - `add_robot` also reaches such a robot through its `scene_xml` |
| `download_assets(action="download")` reports `error` with `No matching robots found.` | The selection matched nothing, so the call fetched nothing - a `robots=` name the registry does not list, or a `category=` no entry carries | The verdict names the unknown entries of `robots=`. `download_assets(action="list")` prints every robot it can fetch with its category |
| `ModuleNotFoundError: trs_so_arm100_mj_description` | Auto-install failed | `uv pip install trs-so-arm100-mj-description` |
| `move_to: the requested POSE is not achievable ... The position ... on its own IS reachable` | The point is fine, the `orientation` is not - a damped least-squares solve honours the rotation and gives up the position, and an arm under 6 DOF (SO-100/SO-101) cannot realize an arbitrary full pose | Omit `orientation=` for a position-only solve, or command the pose on an arm with enough DOF |
| `move_to` reports `EE (body '<robot>/Wrist…')` and low targets fail with a residual of ~0.1 m, or "reach" while the fingers hang above the point | The model ships no tool-point site, so the end-effector frame is a wrist/hand **body** - the SO-100's `Wrist_Pitch_Roll` is ~16 cm behind the jaw tips | Declare the tool point in the registry (`"tool_frame": {"body": …, "pos": […]}`, as the shipped `so100` entry does) or add a `tcp` site to the model; `get_robot_state`'s `end_effector` then reads `site '<robot>/tcp'` |
| `move_to` reached the point but the wrist points the wrong way | `tol` bounds the POSITION in meters; the rotation is bounded by `orientation_tol` in radians (default 0.1, ~5.7 deg) | Read `orientation_error_rad` in the result's json block, and pass a tighter `orientation_tol=` if the default is too loose for the task |
| `move_to: 'orientation_tol' only bounds an 'orientation' target` | `orientation_tol` passed for a position-only move, where it would have nothing to bound | Pass `orientation=[w, x, y, z]` to command a full pose, or drop `orientation_tol` |
| `add_robot` raises after `load_scene` | Scene XML overrides world | Use `add_robot` before `load_scene` |
| `add_robot` refuses with `has no single index to drive it by` | The MJCF declares a multi-control actuator (mujoco 3.12 gives `<pid>` two controls, `<orientation>` up to four), and this backend addresses an actuator by its single control index | Do what the refusal names: it prints each wide actuator and the control slots it owns. Replace it with a single-control actuator (`<position>`, `<motor>`, `<velocity>`, `<intvelocity>`, `<general>`), or drive that joint outside this backend. The refused add leaves the scene as it was, so a corrected model reuses the same name |
| `render(output_path=...)` refuses with `is outside the sandbox` | `output_path` resolved outside the render sandbox (`~/.strands_robots/renders`, `STRANDS_ROBOTS_RENDER_ROOT`, or this Simulation's `render_dir=`) | Write under the sandbox - a bare filename like `frame.png` is placed INTO it, while a relative path with a directory part (`views/front.png`) resolves against the CWD and is refused, quoting the sandbox-anchored spelling to pass instead. Or construct `Robot(name, render_dir="<the directory you want>")` so that directory IS the sandbox. Or set the variable the refusal names: `STRANDS_ROBOTS_RENDER_ALLOW_ABS=1` for `render`, `STRANDS_ROBOTS_VIDEO_ALLOW_ABS=1` for the video sinks under `STRANDS_ROBOTS_VIDEO_ROOT` |
| `move_to` refuses with `is unreachable ... The same target solves to ... once the N degree(s) of freedom move_to does not command are free too` | The target needs motion `move_to` does not produce: it drives the named end-effector frame with position servos only, so a mobile base, a floating pelvis or any unactuated joint is not available to the solve - and 35 shipped sim robots have one | Move those degrees of freedom first (drive the base to the work area), then call `move_to`. The refusal's `uncommanded_joints_moved` names them, and `unrestricted_ik_residual_m` is what the whole robot could reach |
| `move_to`/`rotate_wrist`: `... did not reach ... The servo was stopped: the robot is in contact: 'ground' <-> 'so100/Fixed_Jaw/geom_18' (d=-0.0002 m)` (or `commanded joint(s) at a limit: '...' at its upper limit`) | The servo could not reach the commanded value (for `move_to`, IK had already solved the point): something on the robot pushes against another geom, or a commanded joint sits on a bound of its range. The refusal names the pair (nearest first, at most three, total in `json.obstruction.contacts_total`) and the joint, read at the final tick; an unnamed geom is labelled `<body>/geom_<id>`, as `get_contacts` labels it | Clear what the robot touches, or command a value that avoids it - a position for `move_to`, an angle for `rotate_wrist` - or one the named joint can reach. If the text says `no contact involved the robot and no commanded joint was at a limit`, raise `max_steps` or loosen `tol`: the arm may not have arrived, and a longer run is what reveals a contact ahead of it. `get_contacts` shows the full list |
